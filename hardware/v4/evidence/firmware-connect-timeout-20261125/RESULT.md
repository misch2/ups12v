# Connection timeout follow-up - 2026-11-25

Latest finding: the owner subsequently reported `tls=24960` (`0x6180`,
MBEDTLS_ERR_CIPHER_ALLOC_FAILED) after loading the longer-timeout changes.
This confirms a TLS allocation failure. A compact trust bundle and heap
diagnostics have now been added; on-device recovery is not yet established.

Baseline aa03656; owner firmware version 20261125.9 preserved.

## Owner evidence and diagnosis

Owner-provided UPS4 / HW 4.0 / ESP32-C3 logs show a failed connection with
`sdk=0x7002 tls_sdk=0x8006 tls=0 verify=0 http=0`. The retry then completed:
`state=current; error=none; checked version=20261125.8`. A subsequent .9 boot
reproduced the same timeout. The emitted JSON agrees with these codes.

ESP-IDF 5.5.5 defines 0x8006 as ESP_ERR_ESP_TLS_CONNECTION_TIMEOUT and 0x7002
as ESP_ERR_HTTP_CONNECT. No HTTP response, mbedTLS error or certificate verify
flags were reported. This identifies a connection setup timeout; it does not
establish which network condition caused the delay. The successful retry is
owner evidence that manifest HTTPS, certificate checks and parsing have worked
on the device at least once. It does not validate firmware asset installation.

The first worker request can overlap synchronous HA discovery: firmware service
runs before reconnectMQTTIfNeeded() publishes discovery in loop(). The owner
logs show discovery taking about nine seconds. An effect on connection timing
is plausible, not demonstrated. No startup delay or MQTT dependency was added.

Sources: [ESP-TLS errors](https://github.com/espressif/esp-idf/blob/v5.5.5/components/esp-tls/esp_tls_errors.h),
[connection implementation](https://github.com/espressif/esp-idf/blob/v5.5.5/components/esp-tls/esp_tls.c),
[HTTP API](https://github.com/espressif/esp-idf/blob/v5.5.5/components/esp_http_client/include/esp_http_client.h).

## Focused changes

- Allow 15 seconds for connection setup, instead of using the five-second read
  timeout. Restore five seconds before fetching headers/body. Each redirect
  connection is capped by the remaining 20/180-second manifest/download budget.
- Keep HTTPS, CA/hostname checks, worker scheduling and retry policy unchanged.
- Emit detailed HTTPS failure diagnostics only on entering failed state. The
  old implementation repeated the previous result while entering checking.
  Generic state logs explicitly label the previous result as `last error`.
- Behavioral SDK simulation covers seven-second connections through a redirect,
  exhaustion of the remaining overall budget and a connection beyond 15 seconds.
  Existing worker tests check header/body timeout bounds and transfer/error paths.

## Later live evidence and RAM change

A scoped read-only MQTT snapshot and 66-second trace of UPS4's firmware state
received retained .9 failure, then fresh checking/failed transitions at
20:15:52 UTC. They report `tls_sdk_error=32794` (0x801a), `tls_error=9984`
(0x2700), certificate verification failure. The SDK reports the magnitude of
mbedTLS errors; zero certificate flags do not exclude a verify failure because
the SDK only captures them if a peer-certificate pointer survives the failed
handshake. The later owner's 21:21:45 local boot log reports TLS error 24960
(0x6180), cipher allocation failure. That is direct RAM-failure evidence; whether
the earlier verification failure has the same cause remains unproven.

All four Pages IPv4 addresses validate with the existing PEM roots and RSA TLS
1.2 from this PC. ECDSA-only negotiation is rejected by those endpoints, as
expected for the current RSA certificate. The same chain passes upstream
Mbed TLS 3.6.4 host verification. The device SDK is 3.6.6; the offline library is
not a substitute for matching ESP hardware validation.

The compact 1115-byte asset is generated by official ESP-IDF 5.5.5 tooling from
the exact existing three PEM roots. It embeds the SDK's normal default-bundle
symbols, replacing the full default asset, and uses esp_crt_bundle_attach.
Only certificate subjects/public keys are retained in flash, avoiding per-request
full PEM CA parsing. No roots are added, and TLS/hostname verification stays on.
Python data tests pin its three sorted subjects and public keys. Root changes
must regenerate this asset; ordinary builds use the checked-in binary.

The actual ESP-IDF 5.5.5 bundle verifier compiled with host Mbed TLS 3.6.4 accepts
the real Pages chain and rejects both a wrong hostname and an unrelated generated
CA. This verifies the compact bundle format and verification behavior offline;
RTOS, ESP heap behavior and hardware crypto remain unverified.

New network status and syslog report free internal 8-bit RAM and the largest
contiguous block before HTTP initialization and on failure before cleanup.
These will distinguish insufficient memory from fragmentation in the next owner
test. The bundle's actual on-device saving has not been measured.

## UPS4 .10 on-device manifest check confirmed

Owner uploaded .10 by Arduino OTA. At 21:34:43 local, its first reported check
failed with connection timeout 0x8006. Heap diagnostics then showed 128280 bytes
free / 102388 largest block before setup, and 53776 / 34804 at failure. That

A later check succeeded. A read-only 66-second subscription to only UPS4's
firmware state received retained status `current`, `error=none`, HTTP 200 and
`stage=complete`, with installed .10 and feed .8. No fresh transition was received
during that observation. A subsequent direct read-only GET /firmware/status
confirmed the same result at 2026-11-25T20:37:38.577946+00:00. The successful check
started with 75576 internal bytes free and a 34804-byte largest block. Its exact
completion time and whether it was an automatic or explicit retry were not captured.

This establishes that the compact bundle, TLS verification and manifest parsing
have completed on the real UPS4. It does not establish that every boot will avoid
a timeout, quantify the bundle's RAM saving, or validate asset download/flashing

setup can time out during TCP connection or TLS handshake. No further firmware
